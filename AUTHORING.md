# Authoring a composition

How to write, build, and verify a composition in this repository, starting from
a fresh clone. The reader this is written for has never seen PocketJS.

A composition is a small PocketJS app — JSX components styled with a Tailwind
subset — that this repository renders to MP4 deterministically: the same input
produces byte-identical frames on any machine, verified by per-frame hashes
rather than by looking. The renderer is the same `no_std` Rust core that runs
the framework on handheld hardware; there is no browser, no CSS engine, and no
wall clock anywhere in the pipeline.

The vocabulary is deliberately not all of CSS. What it is instead is small
enough to know completely, and everything in it renders the same bytes every
time. When something you expect from the web is missing, that is usually a
constraint to design with, not an omission to work around — this document lists
the load-bearing ones.

## Setup

```bash
bun install
bun run vendor        # clone upstream at the pinned commit, apply patches, build the wasm core
bun scripts/assets.ts # fetch digest-pinned assets that are too large to track (CJK faces, audio)
```

`bun run vendor` needs a rustup toolchain with the `wasm32-unknown-unknown`
target (`rustup target add wasm32-unknown-unknown`). Rendering needs `ffmpeg`
on PATH. Everything untracked is rebuildable by exactly one of the commands
above; if a file is missing, the error says which one.

Rather than finding out later, ask:

```bash
bun src/cli/main.ts doctor  # is this checkout able to build and render at all?
```

Seven checks, each with a sentence saying what was observed and — when it
failed — the command that fixes it: the running Bun against the one
`baselines/digests.json` was recorded on and the one every built artifact's
`build.json` names; rustup and the wasm target; `ffmpeg` and `ffprobe`
separately, with their version lines; the vendored tree at the pin with the
patches applied; `assets/*/manifest.json` fetched and matching; and free disk
against what a full ledger run was measured to decode (688 MiB — it fails below
that and calls the headroom thin below 3x it).

`ffprobe` is asked for separately because it is separately load-bearing:
footage reads a source's dimensions and duration with it *before* paying for
the ingest, so a tarball carrying only `ffmpeg` fails later and further in.

**`--json` always exits 0** and puts the verdict in `ok`, so an agent asking
what to do next gets the report rather than a shell that threw it away. In a
terminal, without `--json`, a failing check exits 1:

```bash
bun src/cli/main.ts doctor --json  # {ok, checks:[{name, ok, detail, fix}]}
```

A green `doctor` says the tools are present and the pins agree. It says
nothing about whether any composition builds — that is `lint`, `build` and
`check`.

## Anatomy

A composition is a directory under `compositions/`:

```
compositions/<name>/
├─ main.tsx            entry: mounts the app
├─ app.tsx             the component tree (often generated — see gen.ts)
├─ pocket.json         upstream manifest: id, entry, viewport
├─ pocket-motion.json  this repo's sidecar: durationFrames, fps, supersample
├─ pocket.config.ts    optional: named keyframes/animations (Tailwind theme)
└─ gen.ts              optional: the build step that writes app.tsx
```

Do not type those from memory. `init` copies a fixture that already passes,
so the first thing that fails is the change you made rather than the seven
agreements between files you have not read yet:

```bash
bun src/cli/main.ts init compositions/my-card --example copy  # not run: it writes a composition into this tree; tests/init.test.ts drives it end to end
```

Four examples — `smoke` (no generator, no assets), `copy` (build-time
measurement, CJK faces), `footage-tracks` (four clip windows) and
`sound-roles` (one element of each sound role). Without `--example`, a
terminal gets the menu and a script gets told which flag it forgot; both exit
2. It copies the fixture's **tracked** files and prints the commands to run
next, in order.

Three things it will not do, each because papering over it costs more later:

- **`app.tsx` is not copied when there is a `gen.ts` beside it.** That file
  carries a `// GENERATED by …` header; seeding a new composition with output
  whose generator has not run is how a hand edit to a generated file starts.
  Run the generator first — it is the first line `init` prints.
- **An existing non-empty directory is refused.** `init` writes a whole
  composition and does not merge into one that is already there.
- **A target outside `compositions/` is refused.** A composition is a
  resident of this tree rather than a portable directory: its generator
  imports shared code by a path relative to the repository, derives the
  repository root from its own location, and its sidecar names fonts and
  clips repo-relative. Depth inside the tree is fine —
  `compositions/a/b/9x16` works, and every relative import that escapes the
  composition directory is re-resolved for the new depth.

An asset the fixture's sidecar names that is not on disk is also refused,
before anything is written, with `bun scripts/assets.ts` — that is the one
thing copying cannot supply, and a composition whose faces are missing fails
much later and about a path you never typed.

**A new composition is not finished until both ledgers account for it.** Each
refuses to run while any composition in the tree is neither measured nor
excused, so add it to `scripts/digests.ts` ENTRIES (or EXEMPT, with the fact
that keeps it out) and to `scripts/visibility.ts`.

Worked examples, roughly in reading order:

- `compositions/smoke` — minimal static-plus-built-ins, hand-written.
- `compositions/curves` — custom keyframes via `pocket.config.ts`, generated.
- `compositions/copy` — a title card whose line breaks and sizes are *measured*
  at build time (see "Text" below). Copy, palette and fonts come from
  `spec.default.json`. A job is `render --spec`, not an edit of the sample.
- `compositions/lower-third` — a name plate in the lower third, same spec
  contract. Optional logo (missing file is an error) and optional one footage
  track, declared with `tileNodes` / `footageTrack`.
- `compositions/glow`, `compositions/glow-column` — a falloff baked into a
  PNG at build time, written before the rasteriser had a blur and kept as the
  fixture for that technique (`glow-*` now draws one at render time;
  `compositions/filters`). The first is the 取消 button; the second renders
  the column veil at a 140px and a 656px stack, which is what puts
  `rotate-180` on the lower cap into the digest ledger — every assertion about
  the generated source passes with the picture upside down.
- `compositions/faces`, `compositions/stroke`, `compositions/filters`,
  `compositions/gradients` — the mechanism fixtures for named faces, text
  stroke, filter layers and gradient paint: four faces in one frame;
  outside, centred, hollow and keyframed outlines; blur steps, a breathing
  glow, a hard shadow, a rack focus keyframed as a CSS `filter`, and the five
  blend modes over a split ground; multi-stop, angled, radial and clipped-to-
  text gradients with a turning angle and a sweeping stop.
- `compositions/bloom` — an alpha glow and a luma glow (`glow-mode-luma`)
  side by side on the same dark translucent plate.
- `compositions/rename-card` — shutter's opening carried six seconds further:
  a dialog, a name typed into it with the caret at each prefix's *measured*
  width (`openMeasurer` again, one `Text` per prefix), and a close built from
  the arc primitive and one-tick step gates. Its `NOTES.md` records every
  reading taken off the recording, and the gate length is the lesson: a 34ms
  gate sampled at 30fps lands on its own midpoint.
- `compositions/timeline` — fourteen cards on one strip, each sliding to the
  centre, growing, holding and leaving, while the whole strip pulls back and
  returns on every move. Three nested wrappers carry three clocks — a `scale`
  for the zoom, one `translateX` with 29 stops for the strip, a `scale` per
  card for the pop — timed against each other by arithmetic alone. The
  captions are two `Text` nodes at two sizes outside the scaled body, because
  when it was made a scale moved glyphs without resizing them; a resampled
  caption would now grow, softer than a baked one. Its `NOTES.md` records every
  number tracked off a recording: the ruler ticks for cadence and zoom, one
  card followed through its whole pass for the pop.
- `compositions/captions/*` — five caption styles ported from the HyperFrames
  catalog (highlight, kinetic-slam, pill-karaoke, clip-wipe, matrix-decode),
  one transcript, every word at a measured x. Each is a different treatment
  of word timestamps as delays: a `width` growing behind the word, an
  `overflow-hidden` window revealing it, a `color` timeline, a one-tick-gated
  scramble, a directional entrance. `compositions/captions/NOTES.md` states
  what each source did and what it became — and the face lesson: measure
  against the face the build actually bakes.
- `compositions/transitions` — nine scene-to-scene transitions from the
  HyperFrames catalog in one film: a velocity-matched cut, a clip wipe, a
  wash, a tile grid, a match cut, a rubber band, a whip pan with echoes
  standing in for blur, and two flat reveals standing in for a mask. Its
  `NOTES.md` states per segment what the source did, what it became and what
  was lost, and two rules of the baker it ran into: the later animation in a
  comma list wins a shared property, and a shrinking scene shows the root.
- `compositions/masked` — four `overflow-mask` windows: a growing circle, a
  rotated window whose width sweeps a diagonal edge, a rounded card clipping
  its text, and a circle inside a rotated window. Its `NOTES.md` says what
  each took; its sidecar asserts what each is for.
- `compositions/kenburns` — the tile grid video footage draws through, with no
  `footage` in its sidecar at all: its pixels are pushed by
  `scripts/push-probe.ts` (see "Footage" below).
- `compositions/footage-tracks` — the worked example for footage: four windows
  over three clips on one clock, one clip supplying two segments through
  `sourceFrame`, one `fit: "cover"`, one `fit: "contain"`, and one track drawn
  at its own aspect so no fit is needed. Its `gen.ts` writes `app.tsx` and the
  sidecar from one table, because the grid and the drawn tile sizes are one
  fact written twice.
- `compositions/sound-roles` — the worked example for sound: a bed, a
  narration line that ducks it, a cue, and a dialogue line placed on a footage
  track's clock rather than the film's.
- `compositions/nested/a/9x16`, `compositions/nested/b/9x16` — two cuts whose
  paths differ only above the last segment and which declare one
  `compositionId`. There to keep them out of one dist directory; nothing else
  in them is load-bearing.
- `compositions/typography` — every font size outside the pinned `FONT_PX`
  scale, which is what makes the build allocate slots from what the source
  actually uses.
- `compositions/reel` — a full generated deliverable, beat-locked to music, and
  the only composition here at film length. Read it for what the fixtures above
  each show one of, arriving together in one `gen.ts`.

Minimal `pocket-motion.json`:

```jsonc
{ "motion": 1, "durationFrames": 450, "fps": 30, "supersample": 1 }
```

The exhaustive list of sidecar keys, footage fields, font slots, the animation
vocabulary (`pocket.config.ts` theme and `animate-*` literals), and the inputs
the build discovers from class literals and per-composition JSON
(`images.json`, `sprites.json`) is generated as `CAPABILITIES.md`. The
`verified` column is `probed` when a violating input was constructed and
the implementation rejected it, and `pinned` when the stated literal was
found in the named source file and nothing more. When a keyframe or shorthand
below does not build, that table is where the exact refusal is written down.

`fps` must divide 60. `supersample` (1|2|4) renders at N×; `render` downscales
the encode back to the declared viewport (an area average over the subpixels,
which is what supersampling means — lanczos was here and rang on hard edges),
while `trace` digests and
`frame` PNGs stay on the supersampled buffer — the hash covers what the
rasteriser produced, scaling is an encode-side step. Use 2+ when text moves
slowly (sub-pixel motion is quantized at 1×).

**`supersample: N` is half a recipe. The other half is `--density=N` on the
build**, and the two must agree. Glyphs are baked bitmaps, so a supersampled
render against a density-1 atlas draws every glyph as a nearest-neighbour copy
of a cell baked for another size — measurably worse than not supersampling at
all. **The densities do share an advance table** — atlas v4 stores logical
advances, and measured over the shipped faces at three slots each, **0 of 261
HarmonyOS Sans advances and 0 of 324 Noto Sans SC advances move between
density 1 and 2**, line height included. What density changes is the coverage
cell's raster size. A build-time fit still has to measure at the density the
composition bakes at, because that is the slot table the finished pak carries:
pass `density: N` to `openMeasurer`. `check`, `trace`, `frame` and `render` all
refuse a mismatch and print the build command that repairs it, and
`openMeasurer` refuses a measurement build that came back at another density —
nothing in this path fails quietly.

## The vocabulary

Three node types: `View`, `Text`, `Image` (from
`@pocketjs/framework/components`). Styling is Tailwind-subset class literals —
layout (flex, size, inset, gap, padding), color/gradient (`bg-*`,
`from-*`/`via-*`/`to-*` with positions, any angle, radial, arbitrary
`linear-gradient()`, gradient text with `bg-clip-text`), `rounded`, `opacity`, `border`,
`shadow`, 2D/3D transforms, named font faces (`font-[name]`), text stroke,
filters (`blur-*`, `drop-shadow-*`, `glow-*`), blend modes (`mix-blend-*`),
and an arc primitive
(`arc-start-[deg] arc-sweep-[deg] arc-width-[px]`). Arbitrary values use
bracket syntax: `w-[880px]`, `text-[38px]`. The authoritative list of
utilities is the compiler itself — `vendor/pocketjs/framework/compiler/tailwind.ts`;
when a familiar Tailwind name fails to build, check there before assuming a
typo (e.g. `items-baseline` does not exist; `rounded-full` needs a
build-time-known width/height in the same class literal — use `rounded-[Npx]`
when the size is content-driven).

A class literal compiles whole or not at all, so one token the compiler does
not read would cost the node every utility beside it. Written as the whole
value of a `class=` attribute, such a literal stops the build, and the error
names every bad token at its file, line and column. Where the token alone
says why, the message says so, and offers a rewrite only when the rewrite
compiles:

```
error: compositions/my-film/app.tsx:5:19: class "absolute left-[1e-14px] w-[300px] rotate--18" does not compile: unknown utilities left-[1e-14px], rotate--18
  `left-[1e-14px]`: a number in exponent notation is not read — `left-[0.00000000000001px]` compiles.
  `rotate--18`: `rotate-N` takes N >= 0 degrees with no brackets or unit, and 342 is the same angle as -18 — `rotate-342` compiles.
```

The first is what a generator gets from `String(n)` or a template literal
for a number below 1e-6 in magnitude; round before printing
(`n.toFixed(3)`). The rule, its messages and the located error are
`patches/0041-loud-unparseable-class-token.patch`, held by
`tests/catalog.test.ts` G6 and G6b.

**Motion comes from baked keyframe timelines, not from code.** Declare
keyframes and named animations in `pocket.config.ts`:

```ts
import { definePocketConfig } from "../../vendor/pocketjs/framework/src/config.ts";

export default definePocketConfig({
  theme: {
    keyframes: {
      rise: { from: { transform: "translateY(40px)", opacity: "0" },
              to:   { transform: "translateY(0px)",  opacity: "1" } },
    },
    animation: {
      // CSS animation shorthand: name duration easing delay fill-mode
      "rise-in": { value: "rise 700ms cubic-bezier(0.2,0,0,1) 300ms both" },
    },
  },
});
```

then reference them: `<Text class="animate-rise-in ...">`. The compiler bakes
these into per-property timelines the core plays by itself — zero JavaScript
per frame. Built-ins like `animate-pulse` / `animate-spin` also work. Easing
is the full `cubic-bezier()` form; named CSS easings match browser curves
exactly. Class strings must be static literals — the compiler reads them at
build time.

Misspell the name and the build stops, listing the names that do exist:

```
error: PocketJS tailwind: `animate-appear-shiftd` in "animate-appear-shiftd" names no
animation. theme.animation declares appear-sampled, appear-shifted, appear-unplayed,
bounce, ping, pulse, spin (framework built-ins included).
```

It does that for anything you wrote in a `class=` attribute, including a
wrapper whose only class is its animation — `<View class="animate-rise-in">`.
What it will not do is second-guess a string that merely looks like one: the
compiler is offered every string literal in the module as a class candidate,
so a sentence containing `animate-something` compiles to nothing and says
nothing. That is deliberate, and it is why the check reads where the literal
was written rather than what it contains.

The one case still silent is a class assembled out of pieces —
`class={"animate-lid-" + which()}`, or a backtick with something interpolated
into it. A piece is never the whole value of the attribute, so it carries no
evidence and is not recorded; refusing it would report `animate-lid-`, a
half-token you did not write. Write full literals — quotes or backticks, both
are read the same — and every arm of a `?:`, `||` or `??` is checked.

**Timing is quantised twice, and the second one depends on `fps`.** A duration
or a delay written in ms bakes to whole frames at the realm's 60 Hz —
`round(ms × 60 / 1000)` — and the render then samples every `60 / fps`-th of
those ticks, because that is how many the core steps between rasterises. At
30 fps only even ticks are ever looked at, so a 45 ms delay bakes to tick 3 and
is first seen at tick 4. The shift is under one frame and it is not spread
evenly across a stagger: 45/90/135/180 ms bake to ticks 3/5/8/11 and are shown
at 4/6/8/12 — gaps of 2, 2, 4 where four equal ones were written. Nothing here
is nondeterministic and no digest moves; the timing is simply not the timing you
wrote. When the spacing carries meaning, write times that are whole rendered
frames (33.333 ms at 30 fps) rather than round-looking ms, and run
`bun src/cli/main.ts keyframes compositions/<name>` to see which of your
instants the render never samples. At `fps: 60` every tick is rendered and the
question does not arise.

That command also fails on a timeline the composition is too short to reach —
an entrance declared 1500 ms into a 1000 ms film bakes, builds, renders and
holds its first keyframe forever, and `lint`, `check` and `trace` are all green
on it (`compositions/late-anim`).

It reports two more things, each the shape of a defect a composition here
shipped with. **A step the grid lands inside**: a segment no longer than one
rendered frame is a cut, and when its two ticks straddle a sampled one, the
frame taken there shows the cut half done — a `gin 34ms` gate at an odd tick,
rendered at 30 fps, arrives a frame late and grey. A 17 ms gate is one tick
and no frame can land inside it (`compositions/rename-card`'s close uses
those). **A property two animations of one comma list write at once**: the
core takes the LAST animation currently writing a property, and `both` or
`backwards` fill means writing from tick 0, so `gin 34ms linear 0ms both,
slide 600ms ease 400ms both` with opacity in `slide`'s `from` shows that
opacity from the first frame and `gin` never reaches the picture. Put the gate
on a wrapper, where opacities multiply instead of contending
(`compositions/transitions` did). Neither reading fails the command; both are
in its `--json` under `partialCuts` and `contended`, and `late-anim` carries
one of each.

**A window has a shape.** `overflow-hidden` clips children to the node's
axis-aligned box; `overflow-mask` clips them, and the node's own ground, to
the node's OUTLINE — its rounded rectangle under its transform. So a
`rounded-[350px] overflow-mask` window whose `width`/`height` animate is a
growing circle (iris), a `rotate-20 origin-left overflow-mask` window whose
`width` animates is a diagonal wipe, and a `rounded-[40px] overflow-mask` card
clips its text at the corners. Three things to know, each learned the hard
way in `compositions/masked`: write the radius in px, because `rounded-full`
is resolved by the compiler from the size WRITTEN in the literal (0px on an
animated window), while a px radius is clamped to half the box at draw time;
there is no spelling for a negative angle, and `rotate-340` is −20; and to
keep a scene still inside a rotated window, rotate it back about the SAME
point (`origin-left` on both, with the two origins placed on one pixel). A
square-cornered, unrotated `overflow-mask` window whose box lands on whole
pixels is `overflow-hidden` word for word; anywhere else the outline is exact
to a sixteenth of a pixel (`patches/0024`), so content whose edge lies on the
window's edge — a poster seen through a tile of itself — stops at that edge
however the window turns. Content drawn inside it is still placed on whole
pixels (POLY and TEX_TRI are upstream's formats), so a plate offset by a pixel
on purpose rolls away with its tile, a pixel wide. The op is this repository's own (`patches/0013`, the design beside
it): no upstream backend draws it, so a composition that must stay portable to
one keeps to `overflow-hidden`.

**A rounded box keeps its corners when it turns.** A `rounded-*` node under
a rotation, skew or mirror is drawn under its own rounded outline — the one
`overflow-mask` uses — so a turning `rounded-full` circle stays a circle
rather than turning as a square (`patches/0028`). Unturned, it is drawn as it
always was.

**An arc is a stroke.** `arc-width-[px]` turns a node's ground into an
annular sector centred in its box — outer radius half the shorter side,
`arc-start-[deg]` from 12 o'clock clockwise, `arc-sweep-[deg]` long, in the
`bg-*` colour, with a round cap on each end; `arc-cap-butt` ends it on the
radius instead, so an arc as wide as its radius is a pie sector — a radar
wedge, a slice of a pie chart (`patches/0027`). A sweep of 0 draws nothing, neither arc nor box, so a drawn-on
stroke animates `arcSweep` from 0 (`patches/0025`). The arc is drawn in its
node's frame and follows the world transform like any other paint
(`patches/0026`): a ring of arcs on a rotating wrapper turns with it, a
mirror reverses the sweep, and a scale that differs per axis stretches ring,
stroke and caps into an elliptical band.

**Text can carry an outline.** `text-stroke-[6px] text-stroke-[#7c2d12]`
draws a 6 px outline around a Text node's glyphs; `text-stroke-outside` (the
default) grows it outward under the fill, `text-stroke-center` straddles the
glyph edge over the fill, and `text-transparent` with a stroke is hollow text.
The width animates as a keyframe property (`textStrokeWidth`, or
`-webkit-text-stroke-width` in its camel-case spelling `WebkitTextStrokeWidth`)
and so does the colour. A stroke is paint, not layout: the box does not grow,
so an outside stroke is ink past the box and `layout` reports
`text_box_overflow` for it unless the sidecar allows `overflow` for that node
(`compositions/stroke` does, by name). Drawn by this repository's rasteriser
only (`patches/0017`).

**A node can be filtered as a unit.** `blur-md`, `drop-shadow-[6px_6px_8px_#000000]`,
`glow-[24px] glow-amber-400` and `mix-blend-screen` each paint the node and
its whole subtree into one layer, which is blurred, given a shadow and
composited by blend mode when the node is done — CSS's `filter` and
`mix-blend-mode`, in that order. `blur-*` is the standard deviation in px
(Tailwind's 4/8/12/16/24/40/64 steps, or `blur-[Npx]` up to 128); a shadow's
third length is the blur RADIUS, as in CSS, and a shadow draws only with a
colour. `text-shadow-*` is the same shadow under the name CSS uses for text;
`glow-[B]` is a shadow at offset 0, and `glow-gain-[N]` multiplies its
alpha, which is how a thin line of text gets a glow that reads. A shadow is
made from alpha, so a dark translucent plate inside a glow gets a halo under
its whole area and reads lighter than the ground; for light emitted by the
bright pixels only — a bloom — add `glow-mode-luma`: the glow is then made
from each pixel's own colour where its brightest channel is above
`glow-threshold-[t]` (0..1, default 0.5) and added over the content, so the
plate stays dark and a white rule or a cyan bar on it glows in its own
colour (`glow-white` keeps it; another colour tints it; `patches/0033`,
`compositions/bloom`). Everything
but the blend mode animates: write `filter: "blur(16px) drop-shadow(0px 0px
4px #38bdf8)"` in a keyframe, or `blur` / `dropShadowBlur` / `dropShadowGain`
and friends one at a time — `compositions/filters` does both. Like a stroke,
a filter is paint, not layout, and it stays inside the clip in force at the
node; there is no backdrop blur. Layers nest four deep; a fifth paints
unfiltered. What each costs per frame is measured in
`baselines/paint-effects.md` — a glow on each of six lines of lyrics is
about 10 ms at 1080p. Drawn by this repository's rasteriser only
(`patches/0018`).

**Gradients take any number of stops up to six, any angle, and text.**
`bg-gradient-to-r from-red-500 to-blue-500` is the two-stop gradient it
always was, drawn the way it always was. Add `via-white` (50% unless
`via-40%` says otherwise), stop positions (`from-10%`, `to-90%`), an angle
(`bg-linear-45`, `bg-linear-[37.5deg]`, CSS's convention: 0deg points up,
90deg right), `bg-radial`, or write the CSS itself —
`bg-[linear-gradient(30deg,#1e3a8a,#7c3aed_35%,#ec4899_70%,#fde68a)]`,
`bg-[radial-gradient(#fef08a,#f97316_45%,#f9731600)]` — and the node is
painted by a gradient paint instead: up to six stops, `#hex` or palette
colours, `_` for a space, interpolated premultiplied so a fade to
transparent keeps its colour. Radial is about the box centre: the
farthest-corner ellipse by default, `bg-radial-circle` the farthest-corner
circle, and `bg-radial-[circle_closest-side]` or
`bg-[radial-gradient(circle_closest-side,#fff,#0000)]` any of CSS's shapes and
sizes (`patches/0029`) — a round glow on a wide box is `bg-radial-circle`, not
a square box around it. `bg-clip-text text-transparent` with any of
these is gradient text. The angle, every stop colour and every position
animate (`gradAngle`, `gradVia1Pos`, …; `compositions/gradients` turns a
headline's angle and sweeps a via across a bar). Drawn by this repository's
rasteriser only (`patches/0019`).

**Motion blur is a sidecar key, not a filter.** Each frame is otherwise one
tick drawn sharp, so a form crossing 180 px between two frames is shown at
two places with nothing between them. Declare a shutter in
`pocket-motion.json`:

```json
"shutter": { "angle": 180, "samples": 8 }
```

and every frame becomes an exposure: eight renders spread over half the
frame's duration (180 of 360 degrees), centred on the frame's own tick, and
averaged in integers by the core (`patches/0034`). What a sample moves is
narrow, and each limit is a rule rather than a tuning:

- Only translate, scale, rotate and skew timelines are evaluated between
  ticks. Opacity, colour, size, insets and every paint value keep the frame's
  own tick in every sample, so a 34 ms gate opens on the frame it opens on
  without a shutter, and a fade reads the same.
- A sample never crosses a jump: a one-tick segment, a zero-length keyframe
  interval (`50%` beside `50.01%`), a start or end with no fill, a loop or
  iteration wrap whose two sides differ. A cut stays a cut. `keyframes` lists
  every jump a declared shutter will not blur across. A spin through 360
  degrees is not a jump and blurs through its wrap.
- `shutter-hold` keeps the node's OWN timelines at the tick in every sample —
  a fast caption that has to read in every frame. It is not inherited: a node
  is drawn under its ancestors' transforms, so text inside a sliding group
  blurs with the group, and the hold belongs on the group. `lint` warns about
  a hold the source text shows cannot work (`shutter.holdUnderAnimatedAncestor`,
  `shutter.holdsNothing`).
- Tracks started by `animate()`, springs and physics are not baked timelines
  and keep their tick value.

The shutter is an input to identity, `trace` prints it beside the digest, and
there is no flag that could stand in for it. `samples: 1` is refused — it is
the unblurred frame under another identity; remove the key instead. A frame
costs `samples` rasters plus about 1 ms a sample to average at 1080p
(`baselines/shutter.md`); samples sit `speed · angle/360 / samples` pixels
apart, so a fast move wants more of them before the steps stop showing.
`layout`, `visibility` and `assert` ask whether a node is in the picture of
the exposure, and read rects and ink at the tick; `check` renders none and
says so. A probe of the exposure is `samples` renders, so `--read tick` asks
the frame's own tick instead, at one render, and prints that it did and writes
`read: "tick"` into `--json`. It is a different picture: a node only the blur
shows reads covered — `shutter-blur`'s `peek`, under a blade that lies over it
at every tick and turns off it in the samples either side — so the exposure
stays the default. `assert` classifies only the nodes its assertions name.
`compositions/shutter-blur` is the fixture.

**What does not exist** (the checker will catch most of these, but knowing
saves a round trip): per-frame callbacks (`onFrame`), timers (`after`),
effects, signals that change after mount — a composition mounts once and
everything that moves is a baked timeline.

**Mount-only is not "no data-driven timing".** It is *timing has to be decided
before the build*, which is a much weaker constraint than it reads as, and two
independent readers have now mistaken one for the other. Word-level caption
entrances driven by speech-recognition timestamps are the case that keeps
coming up: the transcript exists before the render, so each word's time is
just a number your `gen.ts` turns into an animation delay. Anything you know
at build time — a beat grid, a transcript, a data series, a per-item stagger —
bakes. What cannot exist is timing that only becomes known while the frames
are being produced, and for a renderer that is not a real case. No backdrop
blur, no conic gradients, no radial gradient centred anywhere but the box
centre or sized by a length, no `SCREEN_W`/`SCREEN_H` imports (read the
viewport, or just lay out with flex).

## Text

Two constraints, both absolute:

1. **The renderer does not wrap or shrink text.** A `Text` run breaks only on
   explicit `\n`. Text wider than its box draws past it (or is silently
   clipped by `overflow-hidden`).
2. **Every font size is baked at build time.** Any `text-[Npx]` works, but
   only sizes that appear in class literals get an atlas.

A third edge worth knowing before you animate: **an axis-aligned `scale`
resizes glyphs by resampling the size that was baked.** The run is drawn as
cells sampled bilinearly out of the atlas (upstream 119297b3, on the pin
since 66caf4e5), so a scale above 1 magnifies a bitmap and softens it: for
text that is shown large, bake the large size. `compositions/probe` is the
measurement — at `scale-150` a 64 px bold run's ink goes from 48 to 72 px
tall. Two runs still move without resizing, their cells kept at the baked
size: a rotated or skewed one, and one with a text stroke (`patches/0017`
draws its outline from unscaled cells, so its fill stays unscaled too).
Before the pin moved every scaled run behaved like those two, which is why
`compositions/reel` fades its copy in after a card's scale lands.

So multi-line or fitted text is decided *before* `app.tsx` exists, by
measuring with the renderer's own advance tables. That is what
`src/text/fit.ts` + `src/text/measure.ts` do, and `compositions/copy/gen.ts`
is the worked example: `gen.ts` declares the copy and the boxes, calls
`openMeasurer(...)` / `wrapLines(...)` / `fitToBox(...)`, and emits `app.tsx`
with the `\n` already placed. The measurement is exact — a break decided at
build time *is* layout, not an approximation of it.

A generator that measures the same faces at the same sizes on every run —
a `render --spec` template, a batch — can pass `cache: { charset }` to
`openMeasurer`: the measurement then comes from a metrics-only bake of that
charset (advances and kerning, no coverage, kilobytes per size), built once
and booted per call instead of built per call. A string with a character
outside the charset falls back to the per-call build. The cached pak
measures and cannot be rendered; every render command refuses it.

**Faces.** The sidecar's `fonts.regular` / `fonts.bold` are the default pair
(the build's `--font-regular` / `--font-bold`). `fonts.faces` declares more,
each a named `{ regular, bold }` pair, and a class literal selects one per node
with `font-[name]`:

```json
"fonts": {
  "regular": "assets/fonts/HarmonyOS_Sans_Regular.ttf",
  "bold": "assets/fonts/HarmonyOS_Sans_Bold.ttf",
  "faces": {
    "display": { "regular": "vendor/pocketjs/assets/fonts/InterDisplay-Regular.ttf",
                 "bold": "vendor/pocketjs/assets/fonts/InterDisplay-Bold.ttf" },
    "cjk": { "regular": "assets/fonts/NotoSansSC-Regular.otf",
             "bold": "assets/fonts/NotoSansSC-Bold.otf" }
  }
}
```

`<Text class="text-[120px] font-[display] font-bold">` then bakes its slot
from the display face's bold file. A face with a single weight declares the
same file twice. Every (size, weight, face) triple is its own atlas slot, all
faces sharing one table of 128 (19 pinned for the default pair and mono, 109
allocated in first-sight order); at most 8 named faces, and the declared files
may total at most 64 MiB, each distinct file once. `font-[name]` with a name
the sidecar does not declare fails the build, naming the faces it does.
Measuring for a face means naming it on both sides of `openMeasurer`: pass the
sidecar's `faces` map as `faces`, list sizes as `{ px, bold, face }`, and call
`measure(px, bold, face)` / `lineHeight(px, bold, face)`.
`compositions/faces` sets four faces in one frame.

Files: In-repo:
HarmonyOS Sans (`assets/fonts/HarmonyOS_Sans_*.ttf`); fetched by
`scripts/assets.ts`: Noto Sans SC (`assets/fonts/NotoSansSC-*.otf`) — the only
face here with CJK coverage; upstream's default: Inter
(`vendor/pocketjs/assets/fonts/Inter-*.ttf` — `DEFAULT_REGULAR` in
`framework/compiler/bake-font.ts`; the Inter Display files beside them are
not the default, and measuring against them lands every width 7% short). The atlas bakes only
codepoints that appear in the module's string literals; the measurer refuses
to measure a string its build did not bake, so an unbaked character is a loud
error, not a plausible-looking wrong width.

## Footage

Real video enters as a host-owned tile grid: the sidecar declares it, the
guest declares placeholder `Image` nodes, and the host decodes at build time
(ingest) and uploads pixels every frame. Scaling footage on screen is filtered
correctly up to 2× minification (`linear: true`); beyond that it aliases —
plan shots accordingly.

**A sidecar that declares `footage` gets it presented by every command that
produces frames** — `check`, `frame`, `trace` and `render` build one layer per
track, ingest on demand into `dist/<composition>/footage/<track-id>/` (cached
on everything that can move a pixel), and present each track once per frame.
Each layer holds one decoded frame (`width × height × 4` bytes) for its life;
the rest of the clip stays on disk and is read as `present` walks it. A
1080×1920 track is about 8 MiB, independent of duration. A track that cannot
be built fails the command: a missing source file, no
`ffmpeg`, a `nodePrefix` matching no node, a sidecar `grid` that disagrees
with the tile nodes, or a source whose aspect does not match the drawn size
and has no `fit`. **Nothing renders an empty tile and reports a digest.**

A track is `{id, src, nodePrefix, tile, grid, startFrame, endFrame,
sourceFrame, fit}` (`src/manifest/sidecar.ts`, `FOOTAGE_KEYS`). The three frame
numbers place the clip: the source frame shown at composition frame `f` is
`sourceFrame + (f - startFrame)`, presented while `startFrame <= f <
endFrame`. `endFrame` defaults to `durationFrames`, `sourceFrame` to 0, so one
clip can supply two segments by declaring the same `src` twice with different
offsets. **A window longer than the clip is a build-time error**, raised
before the ingest and naming the largest `endFrame` that would fit — asking
for a frame the clip does not have used to freeze on its last picture in
silence. **A source whose aspect differs from the drawn size is the same
kind of error**, unless `fit` is `cover` (fill and crop), `contain` (fit and
pad), or `stretch` (anamorphic squeeze, the old default made explicit). A
bare `scale=W:H` that would move the far edge by less than one destination
pixel is rounding, not distortion, and keeps today's filter.

**You do not write the guest side. `gen.ts` emits it, from two functions in
`src/footage/declare.ts`:**

```tsx
import { footageTrack, tileNodes } from "../../src/footage/declare.ts";

const PLATE = { w: 640, h: 360 };   // the drawn size, stated once

tileNodes({ nodePrefix: "footage:plate", ...PLATE, tile: TILE, indent: "    " });
footageTrack({ id: "plate", src: "assets/…/clip.mp4", nodePrefix: "footage:plate",
               tile: TILE, ...PLATE, startFrame: 0, endFrame: 150 });
```

`tileNodes` returns the `<Image>` per cell and `footageTrack` returns the
sidecar entry, both derived from that one width and height — including the
`grid`, which is therefore never typed. The reason both come from one place
is that a footage track is **one fact written twice**: the sidecar says
`grid`, the tree says how wide each tile is drawn, and `openFootage` refuses
the track when they disagree — but **the drawn size IS the ingested size**, so
an edit that keeps them consistent and moves both stretches the picture
instead of failing, and nothing downstream can tell.

The names those nodes carry, `<nodePrefix>/tile:<col>:<row>`, are a protocol
between the host and the guest rather than something to compose: the host
builds the string to find the node it uploads into, matches its prefix to read
the drawn size back out of the tree, and needs it to agree with the sidecar at
the same time. `lint` **warns** (`footage.tileNamedByHand`) when it finds one
in a composition's sources that it cannot attribute to a `tileNodes` call — a
text-level check, so it says in the message what it cannot see, and
`openFootage` is still what refuses a track whose tiles are actually missing.

`compositions/kenburns` and `compositions/shimmer` carry tile-shaped names and
are not warned about, correctly: they declare no `footage` at all, their
textures are pushed by `scripts/push-probe.ts` and `scripts/shimmer-probe.ts`,
and `shimmer` draws each tile at an arbitrary size on purpose — which is the
one thing `tileNodes` will not do, because for a bound track the drawn size
has to be the ingested one.

`compositions/footage-tracks` is the worked example, and every clip it draws
is `assets/synthetic/`: three `lavfi` sources whose ffmpeg command and version
are recorded in `assets/synthetic/manifest.json`, so a fresh clone can rebuild
them rather than only verify them. `compositions/kenburns` declares no footage at all —
it is a push fixture whose pixels come from `scripts/push-probe.ts`.
`tests/sidecar.test.ts` has the accepted and rejected sidecar forms;
`tests/footage.test.ts` drives the layer against a manifest built in memory,
so it needs no composition; `src/footage/` is what the host does with them.

## Still pictures

A logo, a seal, a scanned mark — one picture rather than moving footage — is
**baked into the pak at build time**, the same way the faces are. There is no
runtime image loader, and none of the footage machinery above is involved.

**The trigger is a string literal.** `tools/build.ts` collects the
composition's class strings and treats every one matching
`^[\w./-]+\.(?:png|svg)$` as an asset name, so

```tsx
<Image class="w-[512px] h-[256px]" src="wordmark.png" />
```

is the whole declaration. The file is looked for in three places, in order:
the composition's own directory, then `assets/images/` and `assets/` **inside
the vendored engine tree** — `tools/build.ts` resolves those two against its
own root, not this repository's, so `"logo.png"` finds the demo logo shipped
with the engine and this repository's `assets/` is never consulted. In
practice a composition's pictures live beside it.

**Each side is 1 to 2048 px, a power of two or not** (`patches/0020`).
`encodeImageEntry` (`framework/compiler/pak.ts`) throws past that, naming the
size. A 782×398 wordmark goes in as it is; draw it at its own size for a
texel per pixel, or set `"linear": true` for it in `images.json` when it is
drawn larger or smaller. Sprite atlases and tilesets are still powers of two
at most 512 (`TEX_MAX_DIM`), and so is a footage tile — that limit is what
makes footage a tile grid in the first place. The whole image is baked into
the pak: a 2048×2048 picture is 16 MiB there and 16 MiB again in the core.
SVG is rasterised at the composition's density. `compositions/images` draws a
900×506 picture and a 3×5 one.

**An SVG is drawn by the build's own baker, and it draws a subset of SVG**
(`framework/compiler/bake-svg.ts`, `patches/0040`). Its `width` and `height`
are the picture's size in pixels before density, and the `viewBox` is
stretched onto them on each axis independently — `preserveAspectRatio="none"`;
any other value is refused rather than reinterpreted.

| | what is drawn |
|---|---|
| shapes | `<path>` (`M L H V C S Q T A Z`, absolute and relative), `<circle>`, `<ellipse>`, `<rect>` with `rx`/`ry`, `<line>`, `<polyline>`, `<polygon>` |
| paint | `fill` and `stroke`, each `#rgb`, `#rrggbb`, `#rrggbbaa`, `white`, `black`, `none`, or `hole`, which erases what is under it; `fill-opacity`, `stroke-opacity`, `opacity`; `fill-rule` `nonzero` or `evenodd` |
| stroke | `stroke-width`; `stroke-linejoin` `miter`, `round`, `bevel`; `stroke-linecap` `butt`, `round`, `square`; `stroke-miterlimit` |
| structure | `<g>` passes fill and stroke properties to its children; `transform` (`matrix`, `translate`, `scale`, `rotate`, `skewX`, `skewY`) on a shape or a `<g>`, applied in SVG order — the rightmost function first, then each enclosing `<g>` outward; `opacity` on a `<g>`, or on a shape with both a fill and a stroke, composites them as one layer; `style="…"` declarations; `display="none"`; `visibility` |

**What would paint and is not in that table stops the build** with a message
naming it: `<text>`, `<image>`, `<use>`, a `<style>` sheet, `clip-path`,
`mask`, `filter`, `stroke-dasharray`, markers, a gradient `fill="url(#…)"`.
`<defs>`, gradients themselves, `<title>`, comments and editor metadata are
skipped. Two differences from a browser are kept because the icons the engine
ships were drawn against them: a `<path>`, `<polyline>` or `<polygon>` with no
`fill` on it or above it is not filled (a browser fills it black), and a
circle's radius under a non-uniform viewBox takes the smaller of the two
scales.

**Coverage is 16 samples per pixel, and the count is exact.** Each sample row
is crossed once per edge, with the crossing arithmetic of the per-sample
point-in-polygon test the baker used before, so every pixel gets the integer
it always got. `tests/svg-bake.test.ts` holds that against the old baker,
kept verbatim in the vendored tree as `tests/fixtures/bake-svg-reference.ts`:
every SVG the engine and this repository ship that the old baker accepted
bakes to its old bytes at densities 1 to 3 — except two benchmark charts in
the engine's `docs/bench`, whose `<text>` the old baker dropped and this one
refuses — and 1,500 random fills, and 500 whose edges pass exactly through
sample positions, get the same counts. The cost is the edges crossing each
row plus the pixels in each shape's box, not their product: one path of
11,424 edges over 1400×1000 (a 952-cell hex grid) bakes in 63 ms, where
the per-sample test took 23 minutes of CPU.

**A stroke is flattened into fill contours** — a quad per segment, a join on
the outer side of each corner, a cap at each end of an open subpath — and
filled under nonzero, so its edges get the same coverage as a fill. `A` arcs,
circles, ellipses, rounded corners and round joins and caps are subdivided
until each chord is within 1/32 px of the curve. **A cubic or quadratic
segment is always 16 straight steps**, as it was before, and that is coarse
for a large curve: a quarter circle written as one cubic is off the circle by
up to 0.32 px at a 250 px radius and 1.27 px at 1000 px. Draw a large circle
or arc as `<circle>`, `<ellipse>` or `A`, which are not.

**A file that is not found does not stop the BUILD.** It prints

```
image: wordmark.png not found (tried …) — baking a 32x32 placeholder
```

and bakes a checkerboard. Everything downstream then succeeds: the pak is
valid, the render runs, the digest is stable and reproducible. Nothing else in
this pipeline behaves that way — a missing footage source, a missing face and
a window longer than its clip all stop the command.

**`lint` and `check` refuse it.** They discover images the way the build does
— the same regex, over string literals only, across the entry and the relative
imports reachable from it — and fail with `images.missingFile`, naming the
module, the line and every path tried:

```
compositions/<name>/main.tsx:20:40: images.missingFile: image "wordmark.png" is
referenced here and is on disk in none of …
```

`check` asks before it boots, because a clean realm and a stable digest are
exactly what a missing picture leaves behind. `compositions/missing-image` is
the fixture, and it traces green on purpose.

`<compositionDir>/images.json` sets a per-image pixel format (`psm`) where
8888 is not wanted, and a sprite manifest in the same directory bakes an image
as an animated sprite atlas instead of a still.

### Pictures and motion a generator computes

A composition with a `gen.ts` can compute its pictures and its motion
instead of declaring them by hand. Four modules hold what
`compositions/mg-hud` and `compositions/mg-bauhaus` needed, each with a test
whose cases are the defects that reached a film first:

- **`src/anim/sampled.ts`** samples an element's centre, angle, scale and
  opacity on the 60 Hz tick with the easing applied there, and writes linear
  keyframes, so a turn about any pivot is an exact arc and a landing is where
  it was computed to be. `Reg` collects keyframe sets and named animations
  for `pocket.config.ts`; `El` is one element over the film. It refuses what
  would otherwise surface later or not at all: more than 250 keys in a track
  (the baker holds 255 segments), a `step` whose changes do not strictly
  increase (its `t − 1` and `t` keys cross and bake as a ramp from tick 0),
  and an empty `window`. `El.path` after `set` on the same tick keeps the
  state before the change. `tests/sampled.test.ts`.
- **`src/image/raster.ts`** paints line art and imagery analytically into
  plates — rings, discs, wedges, hex grids, traces, polylines with a soft
  edge, speed lines, a synthetic SAR chip — at a cost of the pixel count,
  where the build's SVG baker tests every subsample against every contour.
  `encodePlate` writes the PNG through upstream's encoder; `turnPlate` turns a
  plate by quarter turns as an exact permutation. **A turn a picture keeps
  belongs in its pixels:** the core draws a turned textured quad as two
  triangles whose shared diagonal shows as a faint line. `tests/raster.test.ts`.
- **`src/image/print.ts`** rasterises printed forms — box, disc, quarter,
  half, triangle — from signed distances with a press's wandering edge and
  uneven ink, and cuts a poster made of them into cells from the same fields,
  so cells placed side by side are the poster again with no seam.
  `tests/raster.test.ts`.
- **`src/text/outline.ts`** sets a word in a face's own outlines, scaled so
  its ink fills an exact box, reading across or up, and cuts it between
  glyphs into one plate per letter. Glyph positions come from the same
  kerning `getPath` applies, GPOS included. `tests/outline.test.ts`.

## Sound

Sound is a sidecar declaration, not something a shot file names. The four
roles live under an optional root key `sound`. Absent means no sound — the
parser materialises empty `narration`, `dialogue` and `cues` arrays and omits
`bed`.

| role | clock | placement |
|---|---|---|
| `bed` | composition | `startAt` (seconds into the source; default 0) |
| `narration[]` | composition | `startFrame` |
| `dialogue[]` | the clip's | `track` + `sourceFrame` |
| `cues[]` | composition | `atFrame` |

A bed and a beat-pinned cue belong on the composition clock: the shots
contain no audio references, so a recut does not invalidate the mix. That
is the discipline `compositions/reel/sound.ts` already states, and why
re-cutting the reel never broke its sound.

Dialogue is the role that does not work that way. In-scene speech belongs
to the shot it came from. Pinned to the composition's timeline it
desynchronises the first time that cut is retimed, and no gate would see
it. So a dialogue line names a declared `footage[].id` and a frame on
**that clip's** clock. The composition frame it lands on is the footage
mapping inverted: `track.startFrame + (line.sourceFrame - track.sourceFrame)`,
presented while `track.startFrame <= f < track.endFrame`. A line whose
derived start sits outside that window is refused.

Worked example — a bed, a narration line at composition frame 30 that
ducks the bed to 0.2, and a line of speech at clip frame 12 of `a-roll`:

```jsonc
{
  "motion": 1, "durationFrames": 900, "fps": 30,
  "footage": [{ "id": "a-roll", "src": "assets/synthetic/bars-9x16-30fps.mp4",
                "nodePrefix": "footage:a-roll", "tile": 512, "grid": [3, 4],
                "startFrame": 0, "sourceFrame": 0 }],
  "sound": {
    "bed": { "src": "assets/audio/silent-descent.mp3", "startAt": 0, "gain": 0.5,
             "fadeInMs": 600, "fadeOutMs": 1800 },
    "narration": [
      { "id": "vo-open", "src": "assets/audio/vo.wav", "startFrame": 30,
        "gain": 1, "duck": 0.2 }
    ],
    "dialogue": [
      { "id": "zhou-1", "src": "assets/audio/zhou-1.wav",
        "track": "a-roll", "sourceFrame": 12, "gain": 1 }
    ],
    "cues": []
  }
}
```

`id` values are one namespace across narration, dialogue and cues, so a
mixer can address any element by id. Gains are linear, in `0..8`; `duck`
is the linear gain applied to the bed while that narration line runs
(`0..1`; default 1 is no duck). `cues` is here because the reel already
has beat-pinned spot effects — a schema for narration and dialogue alone
would drop that.

A declared file that is not on disk fails `lint`. There is no candidate
list and no bed-only fallback: if the file is not at the path written in
the sidecar, the command exits 1. A missing path under `assets/` names
`bun scripts/assets.ts`, the same way a missing declared face does.

`check`, `frame` and `trace` do not look at sound. Sound cannot move a
pixel. **Sound is outside frame-digest identity by construction**: audio
is a separate mux pass and the frame hash never opens an audio file, so
a sound declaration changes the delivery and never a pixel. `trace`
agreeing with itself does not say the mix is present, or that the files
resolve.

`render` does. After the frames are encoded it builds the mix graph from
the sidecar (`src/sound/mix.ts`), muxes it under the video stream
(copied, not re-encoded), and writes a sibling `*.sound.json` with the
mixed audio's sha256 (the soundtrack decoded to s16le / 48 kHz / stereo)
and the ffmpeg version that produced it — the same first-line convention
ingest uses. Nothing in that pass is reachable from `trace`.

Ducking is a computed envelope, not a compressor. `duck` on a narration
line is the linear factor applied to the bed's gain while that line
runs; the window is the line's `startFrame` plus the file's probed
duration. A `sidechaincompress` would make the mix depend on content.

Four more shapes are declared in the same block, each in place of a mix
that used to be built by hand around the schema:

- **`envelope` on any element** — points `{ "frame", "gain" }`, linear
  between them, multiplying that element's `gain`, the last value held.
  `frame` counts composition frames from **the element's own start**: frame
  0 is composition frame 0 for the bed, `startFrame` for a narration line,
  `atFrame` for a cue, and the derived frame for a dialogue line — so an
  envelope moves with its element, and a dialogue line's stays on its clip.
  The first point is at 0, frames strictly increase, 2 to 64 points.
- **`bed.ducks`** — windows `{ "startFrame", "endFrame", "duck" }`, half-open
  like footage's, in which the bed is multiplied by `duck` whatever is
  playing: a whole cut at one level, where a narration line's `duck` lasts
  only as long as its file. Windows multiply each other and narration ducks
  where they overlap. The bed's level is `gain` × `envelope` × every window.
- **`optional: true` on any element** — mixed when its file is on disk,
  skipped when it is not. `lint` does not refuse it; `render` prints which it
  was and writes `mixed` per element into the `*.sound.json` record; `sound`
  and `sound --verify` report it `skipped`. Without the flag a missing file
  is refused, exactly as before.
- **`silentTailMs`** — the last N ms of the delivered audio are digital
  silence. The mixer stops all sound 50 ms before the tail and the bed's
  fade-out completes there, because the encoder carries sound one frame
  window past its last input. `render` measures the tail **after the mux**,
  every sample of the s16le / 48 kHz / stereo decode the record hashes, and
  exits 1 when one is not zero. An element that starts at or after the point
  where sound stops is refused by the parser, and one whose file runs past
  it by `render`, which has probed its length. A `--frames` render of
  another length carries no tail.

```jsonc
"sound": {
  "bed": { "src": "assets/synthetic/bed-220hz-8000ms.wav", "gain": 0.3,
           "fadeInMs": 600, "fadeOutMs": 1200,
           "ducks": [{ "startFrame": 30, "endFrame": 150, "duck": 0.5 }] },
  "dialogue": [{ "id": "dialogue-1", "src": "assets/synthetic/dialogue-660hz-1500ms.wav",
                 "track": "clip", "sourceFrame": 80,
                 "envelope": [{ "frame": 0, "gain": 0 }, { "frame": 3, "gain": 1 },
                              { "frame": 36, "gain": 1 }, { "frame": 45, "gain": 0 }] }],
  "cues": [{ "id": "cue-2", "src": "assets/synthetic/sting-not-shipped.wav",
             "atFrame": 120, "optional": true }],
  "silentTailMs": 500
}
```

A varying level is evaluated every 480 samples (`asetnsamples` ahead of the
`volume`), so a duck or a ramp lands within 10 ms of its frame; a WAV leg
otherwise arrives in 85 ms frames and a duck engaged up to that late.

`bun src/cli/main.ts sound compositions/<name>` prints what the sidecar
declares, whether each file is on disk, and the composition frame every
dialogue line lands on. `sound compositions/<name> --verify <file.mp4>`
reads a produced mix and reports, per declared element, whether that
element contributed: the mix is rebuilt without it and the residual is
measured in 100 ms windows (floor −50 dBFS). A bed already playing at
that offset cannot hide an absent line — the bed is in both signals and
cancels. The windows are spread across the span the element claims
rather than taken only at its start, so a line that muxes and then
stops early reports `truncated` and one that never arrives reports
`unmuxed`. A bed is sampled **after** its `fadeInMs`: inside that fade
a correctly muxed bed is legitimately near silence — at gain 0.14 it
measures −69 dBFS at the top of a 1.5 s fade, well under the floor —
so sampling from the declared start reports a present bed as
`truncated`. For the same reason a window where the element's
**declared** level leaves it under the floor — an envelope at 0 — is
dropped rather than read as the element stopping.

Where the declaration **varies** a level — an `envelope`, a `ducks`
window, a narration `duck` — it measures that level once per piece
between breakpoints: the residual less the source, read through the mix's
own channel layout, must lie within the declared range over that window,
±1 dB. The expected level comes from the sidecar's numbers, not from
rendering the graph, so a graph that dropped the envelope is a
`level-mismatch` rather than agreeing with itself. A declared silent tail
is read sample by sample. It **does not** check a constant level, the
fades, overlap, or that the file is the right audio: a wrong file at the
right offset produces a residual and passes, and a gap shorter than the
spacing between windows is not seen. A source that is itself silent is
reported as `source-silent` and a declared level that leaves nothing above
the floor as `declared-silent`; neither is a pass.

`compositions/sound-roles` declares one element of each of the four roles
and one of each shape above, and is the worked example: its tones are
`assets/synthetic/`, and its dialogue line sits at clip frame 80 of a track
that starts at composition frame 30 from clip frame 20, so `sound` prints
composition frame 90. Its bed is ducked to 0.5 for the cut the clip is on
screen, its dialogue line carries an envelope, its second cue is optional
and deliberately not in the tree, and its last 500 ms are silent. `render`
reports the cue skipped and the tail silent; `sound --verify` on that mix
reports four `present`, one `skipped`, every level window in range and the
tail met. `compositions/reel` declares its bed in the sidecar and is mixed
by `render`.

## Build, then verify

**`verify` is the gate, and everything else in this section is either how you
get an artifact for it to read or how you read one of its sections on its
own.** It runs `lint`, `check`, `keyframes`, `visibility`, `layout` at sampled
frames and `assert`, in that order, and prints one JSON envelope whose
sections are those commands' own output verbatim; the exit code is decided by
the sections that failed. Its own subsection is below, after the commands it
is made of.

Build first (the CLI's error messages print this exact command when an
artifact is missing):

A job is a JSON spec (`spec: 1`, `template` names the generator). Unknown keys
are refused. `gen.ts` with no arguments uses `spec.default.json` and rewrites
the sample. `render <dir> --spec job.json --out out.mp4` stages a throwaway
copy of the composition, generates into it, builds, encodes, then removes the
tree — the sample is not a job. A directory of jobs is
`render <dir> --spec jobs/ --out-dir out/`. `preview <dir> --spec job.json`
builds that job and opens `/watch`. User copy becomes a text literal; palette
hex becomes a class literal the generator writes. A job is a complete spec,
not a patch on the sample: `--frames`, `--fps`, `--width`, `--height`,
`--supersample`, `--bundle` and `--pak` are refused with `--spec`. `copy`
is a title card;
`lower-third` is a name plate (optional logo, optional one footage clip).
`glow: true` bakes a vertical veil behind the copy/name column at build
time: a constant fill stretched to the column and the stack, and two caps
whose falloff stays at native σ (a still picture baked at build time; a
generator written today could use `glow-*` instead). Omit it to leave the
sample's picture unchanged. A logo is a still picture (each side at most
2048 — see Still pictures above). Footage is ingested into the throwaway job tree and deleted with it,
so a batch of jobs sharing one clip still decodes it once per job. The
digest in `render --json` is the job's picture at a fixed `--hash`;
`trace` does not accept `--spec`, so a job is not in the identity ledger.

```bash
bun compositions/copy/gen.ts     # only if the composition has a generator
bun src/cli/main.ts build compositions/smoke
bun src/cli/main.ts build compositions/layout-codes
```

`build` spawns upstream's `tools/build.ts` with the argv every command prints
— the same one the ledger runs — and then writes `build.json` beside the
bundle: the Bun, the pinned upstream commit, every patch by sha256, and that
argv. **Every command that reads a bundle refuses one with no `build.json`
beside it**, the way a bundle that does not publish its bake rate is refused,
so a hand-run `bun vendor/pocketjs/tools/build.ts …` leaves artifacts nothing
here will render. The refusal says which command to run. A recorded Bun that
is not the running one, and a `patches/` that has changed since, are refused
the same way and name what moved.

`copy` and `lower-third` regenerate their sample from `spec.default.json`; a
job is `render compositions/copy --spec job.json --out out.mp4`, and many jobs
are `render compositions/lower-third --spec jobs/ --out-dir out/`.

**The `--outdir` is derived, not a name.** There is one dist root — the
repository's own `dist/` — and a composition builds into its path below it, at
any depth: `compositions/copy` into `dist/compositions/copy`, a nested cut at
`compositions/nested/a/9x16` into `dist/compositions/nested/a/9x16`. Every
command prints the whole recipe when an artifact is missing, so copying it is
always right; a `--outdir` written by hand builds successfully into a
directory nothing reads and leaves `check` reporting `bundle not found: …`
against the path it did expect.

**Declare the faces in the sidecar rather than only in a comment.** They are
part of the render's identity — the same composition against another face is
another set of advances and another digest — so a composition that does not
say which face it uses has a digest nobody else can reproduce:

```jsonc
{ "motion": 1, "durationFrames": 1350, "fps": 30, "supersample": 1,
  "fonts": { "regular": "assets/fonts/NotoSansSC-Regular.otf",
             "bold":    "assets/fonts/NotoSansSC-Bold.otf" } }
```

Paths are repo-relative, both weights or neither. With the field present the
build command every command prints carries `--font-regular` / `--font-bold`,
and a declared face that is not on disk fails with the fetch command rather
than building against upstream's default without saying so. Omit the field and
you get that default (Inter), which is the right answer for a
composition that has no opinion.

Then the command surface — every command takes a composition directory and
supports `--json` (one JSON object on stdout). `lint` / `check` / `trace` /
`frame` / `render` / `diff` / `layout` / `sound` never need a browser.
`preview` opens a player at `/watch` (time, fullscreen, speed, volume, loop)
over an MP4 this command encodes the same way `render` does. Both it and `/`,
the frame debugger, read positions as frames — the `f N/last` box takes the
same number `frame --at` and `layout --at` do, and the arrow keys step one
frame, or a second with shift. `/` is where the browser is a display and Bun
still seeks and hashes. `--no-open` prints the URL and leaves the tab alone.

Both pages carry a rail listing every composition in the tree; picking one
points the running host at it, so a second composition does not need a second
`preview`. Rows are named by path rather than by `compositionId`, because two
pairs here share an id. A composition whose bundle has not been built is
listed and refused with the command that would build it; one whose
`pocket-motion.json` will not parse is listed with the diagnostic that says
which key and why.

`/watch` shows the session's own frames from the moment it opens and swaps to
the encoded film when there is one — scrubbing, stepping and the frame box
never needed the file, only playing at speed does. The line in the corner says
how far the encode has got. The last four compositions you watched keep their
viewing copy, so switching back to one of them is immediate.

`preview` watches `compositions/` while it runs. An edit anywhere in the tree
rebuilds the composition on screen — the same build command printed above. If
that build changes the bundle or the pak, the session reopens and both pages
follow: `/` re-renders the frame it is sitting on, `/watch` re-acquires the
film and lands back on the frame it was showing. If it does not — you edited a
different cut, or changed a comment — the pill says so and nothing reopens,
because the whole tree is watched and a boot plus a re-encode is not what a
save somewhere else should cost. `--no-watch` turns the watching off, and the
line the command prints on startup says which it is. Switching back to one of
those four costs nothing; a viewing copy is kept until its bundle moves, until
a fifth composition pushes it out, or — if it was still encoding when you
switched away — until you switch away.

**Every line below is executed by `tests/authoring.test.ts`**, in order, in a
scratch copy of the tree — so a flag that stops existing fails a test rather
than an author. The composition named is a real one, and a line the gate
cannot run says why in a `# not run:` comment rather than being quietly
skipped.

```bash
bun src/cli/main.ts verify compositions/smoke --samples 3  # every gate below, one envelope, one exit code
bun src/cli/main.ts lint   compositions/smoke   # sidecar valid? mount-only? every referenced image on disk?
bun src/cli/main.ts check  compositions/smoke   # boots? realm clean? mount-only at runtime?
bun src/cli/main.ts trace  compositions/smoke   # per-frame hash sequence + digest
bun src/cli/main.ts frame  compositions/smoke --at 120 --out /tmp/f120.png
bun src/cli/main.ts layout compositions/smoke --at 200  # where everything landed
bun src/cli/main.ts layout compositions/layout-codes --at 0  # one named node per finding code
bun src/cli/main.ts keyframes compositions/smoke  # the baked timelines, on the grid the render samples
bun src/cli/main.ts visibility compositions/smoke  # over sampled frames: is a named node never shown, or shown then buried?
bun src/cli/main.ts assert compositions/layout-codes  # do the sidecar's assertions[] hold?
bun src/cli/main.ts sound  compositions/sound-roles  # what sound is declared, and does each file resolve?
bun src/cli/main.ts render compositions/smoke --out out.mp4
bun src/cli/main.ts diff trace-a.json trace-b.json  # not run: two files you write with `trace --json`; first divergent frame, or none
bun src/cli/main.ts sound compositions/sound-roles --verify out.mp4  # not run: needs that render first; did each declared element contribute to this mix?
bun src/cli/main.ts preview compositions/smoke  # not run: holds a port until you interrupt it; /watch player, / frame debugger
bun src/cli/main.ts preview compositions/copy --spec job.json  # not run: a job spec you write, and a port
bun src/cli/main.ts render compositions/copy --spec job.json --out out.mp4  # not run: a job spec you write; tests/spec.test.ts drives this path
bun src/cli/main.ts render compositions/lower-third --spec jobs/ --out-dir out/  # not run: a directory of job specs you write
```

### Delivery formats

`render --format` takes one of four. The encode leg is the only thing any of
them changes: frames are hashed before a byte reaches it, so **a
composition's digest is the same whichever format you ask for**, and
`tests/format.test.ts` asserts that rather than leaving it to be believed.

| `--format` | what it writes |
|---|---|
| `mp4` (default) | libx264, `yuv420p` — unchanged |
| `webm` | libvpx-vp9, `yuv420p`; `--alpha` → `yuva420p` |
| `mov` | ProRes 422 HQ (`yuv422p10le`); `--alpha` → ProRes 4444 |
| `png-seq` | `<out>/%06d.png`, no ffmpeg at all |

```bash
bun src/cli/main.ts build  compositions/alpha
bun src/cli/main.ts render compositions/alpha --format mov --alpha --out /tmp/alpha.mov
bun src/cli/main.ts render compositions/alpha --format png-seq --out /tmp/alpha-frames
bun src/cli/main.ts render compositions/alpha --format mp4 --alpha --out /tmp/alpha.mp4  # exit 2
```

With no `--format` the `--out` extension decides. **A `--format` that
disagrees with the extension is refused**, because a `.webm` holding H.264
plays, reports a sensible duration, and is not what it says it is. `png-seq`
writes a directory, so its `--out` must not carry an extension.

`png-seq`'s frames are **the same PNG bytes `frame --at N` writes** — asserted,
not intended, the way `preview`'s `/frame` is. It is the format to reach for
when the next tool in the chain is not a player. It is also the one format
with nowhere to put a mix: a composition that declares `sound` rendered to
`png-seq` says so in the output rather than losing it quietly.

**`--alpha` delivers a picture.** The rasteriser clears the framebuffer to
*transparent* black (`patches/0014-transparent-clear.patch`), so a pixel that
no declared ground reaches has alpha 0, a partially covered edge carries its
coverage in the alpha byte with its own colour intact, and a composition whose
root declares a `bg-*` is opaque everywhere, exactly as it rendered before the
patch. Rather than state that and let it go stale, `render --alpha` measures
the smallest alpha byte it saw and prints it:

```
alpha floor 0 — the frames are transparent where no ground was declared
```

`compositions/alpha` is the fixture: the one composition here with no declared
ground. `tests/format.test.ts` asserts its floor is 0. A transparent delivery
is a composition with no root ground rendered to `mov --alpha`, `webm --alpha`
or `png-seq`.

`--alpha` with `mp4` is **refused**, not ignored: this project encodes H.264 as
`yuv420p`, which has no alpha plane, and accepting the flag would drop the
channel without saying so.

Two things reading the flags would get wrong, both pinned by the tests:
ProRes 4444 is asked for as `yuva444p10le` and *decodes* as `yuva444p12le`,
because the 4444 bitstream is 12-bit; and VP9 stores alpha out of band, so an
alpha WebM's stream still reports `pix_fmt=yuv420p` and the evidence is the
container's `alpha_mode=1`.

### What `--json` will and will not say about your machine

Every `--json` envelope leaves through one function (`src/cli/emit.ts`), so
the rule is the same for every command and there is one place to read it:

- a path inside the checkout is rewritten to `$REPO/…`;
- a path anywhere else under your home directory is rewritten to `$HOME/…`;
- a path that names neither — `/usr/local/bin/ffmpeg`, `/tmp/out.mp4` — is
  left alone, because it says what software the machine has rather than who
  is running it.

Paths inside a sentence are rewritten too, so the build command quoted back
by a refusal is safe to paste somewhere else. **Diagnostics on stderr are
not redacted**: those are for the terminal you are in, where the real path is
what you type back.

Set `MOTION_RUN_ID` and every envelope carries it back as `runId`, which is
what joins one turn's `lint`, `check`, `trace` and `visibility` output after
the shell that ran them is gone. An unset or empty variable adds no key:

```bash
bun src/cli/main.ts lint compositions/smoke --json  # $REPO/… paths; MOTION_RUN_ID comes back as runId
```

Then the two ledgers, which are the steps that are not per-composition:

```bash
bun scripts/digests.ts                 # every listed composition still digests the same
bun scripts/digests.ts --only <name>   # narrow what runs
bun scripts/digests.ts --write         # re-record, after an intended change

bun scripts/visibility.ts              # every composition, swept for buried nodes
bun scripts/visibility.ts --write      # re-record, after an intended change

bun scripts/catalog.ts                 # is CAPABILITIES.md current? (--write regenerates it)
```

`scripts/visibility.ts` is the digest ledger's shape applied to what is on
screen. Per composition it holds the failing node names, how many nodes carry
a `debugName`, and how many paint and are never shown — so deleting a
`debugName`, which nothing else in the tree would notice, shows up as the gate
covering less than it did. `compositions/occluded` records a failure by name,
because that fixture is the defect and a clean run there means the check
stopped working rather than the film got better.

**A new composition does not pass until it is accounted for in both.** Each
run first checks that every composition in the tree is either covered or
excused in `EXEMPT` with a written reason, and refuses otherwise. In
`digests.ts` being measured is what a composition earns; in `visibility.ts` it
is the default and staying out is what costs a sentence:

```
compositions/<name>: neither measured nor excused. Add it to ENTRIES, or to
EXEMPT with the fact that keeps it out.
```

Measured is the default. `EXEMPT` costs a sentence saying what keeps the
composition out — a fixture with no output to reproduce, a variant whose digest
is another entry's. That sentence is checked for being non-empty, and an
`EXEMPT` name with no composition behind it fails too, so a rename cannot leave
a stale excuse behind.

The build command is not written in that script: it comes from
`resolveComposition`, the same string every CLI command prints when an artifact
is missing. So the ledger checks the recipe above, not a private one.

`layout` answers the half of the question `openMeasurer` cannot. Measurement
tells you how wide a string is before it exists; `layout` tells you where the
renderer actually put it, as border-box world rects:

```
layout at frame 0 — 3 node(s), viewport 1920×1080
    POCKETJS MOTION · 确定性视频渲染   360,286    1200x41     28px
    把网页那套写法用来写视频，但
不要浏览器       360,359    1200x220    76px
    文字的断行在构建期就定好了：先问渲染器每个字形的步进宽度   360,647    1200x147    34px
```

That is `compositions/copy` at frame 0. The middle row spans two printed lines
because the `\n` in it is real — the break was decided by measurement in
`gen.ts` and is part of the string the node draws.

**Read it to write an assertion, not to nudge a number.** The loop that pays
here is the one the generators in this repository already use: decide the
intent in `gen.ts`, assert it, and let the build fail when it stops holding —
`compositions/sound-roles` re-derives its dialogue line's composition frame
and refuses when its own constant disagrees, and `compositions/reel` stops the
generator rather than let a declared cue vanish from the mix. A rect you
eyeball once and hard-code is a number that goes stale the next time the copy
changes.

Two things about the numbers: a rect is captured before the opacity cull, so a
faded-out node still reports its box (useful — you can ask where something
will be — but a rect is not proof anything is on screen), and a `Text` node's
rect is its box, since the characters inside are one glyph run.

`inPicture` is the other half: a node is in the picture only if hiding it at
draw time changes a pixel, which covers occluded, opacity 0, off-screen,
zero-size and time-inactive in one test. `--json` also carries `notInPicture`,
the count of named-or-text nodes that have a box and paint nothing — the number
the header line prints.

**That count is not a defect count, and `layout` exits 0 either way.** Measured
across the 21 ledger compositions at five frames each, **46 of 114 sampled
frames hold at least one**: a node whose window has not opened yet, or a cut
boundary where the outgoing shot still carries boxes under the incoming one.
Whether an out-of-window node appears here at all depends on where the fade is
animated — on the node, and its own rect is captured before its own cull, so it
is reported dark; on a wrapping parent, and opacity 0 culls the subtree, so the
children come back rect -1 and are not reported at all. Same intent, two tree
levels, two different reports.

Which of the two a dark node is, `layout` does now say, in a word next to it:

```
   buried                       80,80      316x44     laid out, not in picture — covered
```

`covered` means the node emitted geometry and no pixel of it survived —
something painted over it. `declared-invisible` means it emitted no geometry at
all: faded out, off screen, zero-sized, or inside a parent whose opacity is 0.
The first is usually a mistake and the second usually is not.

### Finding codes

Those two readings are the last two of seven codes `layout` prints beside a
node and carries in `--json` as `findings[]`. A code is a name for something
exact, so you can branch on one instead of reading a paragraph:

| code | what was examined |
|---|---|
| `text_not_painted` | the node emitted no geometry at this frame |
| `text_occluded` | it emitted geometry and no pixel survived |
| `panel_out_of_canvas` | the canvas clamped its box to zero extent — it is wholly off screen |
| `escaped_container` | its box leaves the box of its nearest ancestor that has one |
| `content_overlap` | two NAMED nodes on screen share positive area, neither containing the other |
| `text_box_overflow` | its INK reaches outside its own box — the run is wider than the box |
| `clipped_text` | its box crosses its container's edge and its ink stops at that edge |

The last two are measured in pixels, by hiding the node and taking the
bounding box of what changed. That is the same test `inPicture` rides on and
costs no extra render — and it means a glyph drawn in the colour of what is
under it contributes no ink and is not seen here, which is the blind spot
`covered` has for the same reason.

`panel_out_of_canvas` is narrower than it sounds and the reason is worth
knowing before you rely on it: **layout clips every box to the viewport before
anything can read it.** A node declared at `left-[2000px] w-[300px]` on a
1920-wide canvas comes back `1920,y 0x120`, and one 200 px tall starting 40 px
above the bottom comes back 40 px tall. So a PARTIAL overhang leaves no trace
in the numbers and this code says nothing about one; what it catches is the
node that went off entirely and collapsed against the edge.

**`layout` still exits 0 with every one of them.** A node outside its window is
not painted, an intended lower third does overlap the shot under it, and a cut
boundary has the outgoing shot's boxes under the incoming one. `verify
--strict` is what turns a finding into an exit code.

**Say so in the sidecar when a finding is the shape you meant.** `layoutAllow`
takes a node's `debugName`, one of four scopes, and a sentence:

```jsonc
{ "motion": 1, "durationFrames": 240, "fps": 30,
  "layoutAllow": [
    { "node": "wing",
      "allow": "overflow",
      "reason": "the cap is drawn wider than the frame it hangs on; leaving the box is the shape" }
  ] }
```

`overlap` covers `content_overlap`, `overflow` covers `escaped_container`,
`text_box_overflow` and `clipped_text`, `occlusion` covers `text_occluded` and
`text_not_painted`, and `canvas` covers `panel_out_of_canvas`. The finding stays
in `--json` with the sentence attached as `allowedBy`, and drops out of
`findingCounts` — a suppressed reading nobody can read back is worse than a
noisy one. The `reason` is required and checked for being non-empty; it is not
matched against anything. An allowance on either participant excuses a
`content_overlap` pair, because the intent is about the two of them.

`compositions/layout-codes` is one named node per code, plus one the sidecar
excuses; the command fence below prints all seven from it.

### `snapshot` — several frames, and what is in them

`frame --at N` is one PNG and `layout --at N` is one report. Reading a film
means both, at several frames, side by side:

```bash
bun src/cli/main.ts snapshot compositions/layout-codes --out sheet/ --samples 6
bun src/cli/main.ts snapshot compositions/layout-codes --out sheet/ --at 0,12,29 --annotate
bun src/cli/main.ts snapshot compositions/layout-codes --out sheet/ --at 0 --zoom cut-off
```

`--samples N` spaces frames evenly with both ends included — the same grid
`visibility` sweeps, from the same function, so a frame number read off one
carries to the other. `--at a,b,c` names them instead.

**The un-annotated PNG is the same bytes `frame --at N` writes**, asserted in
`tests/snapshot.test.ts` rather than intended. `--annotate` writes a SECOND file
beside it — `frame-000000.annotated.png` — with a box round every node that
carries a finding, its name and codes above it, and a thin white box for the
node's ink where that was measured. The overlay is drawn host-side on a copy of
the pixels and never through the composition: a debug layer inside the guest
would be geometry in the draw list and would move the frame hash, so every
reading after it would be a reading of a different picture. `--zoom <debugName>`
writes a crop around that node, padded, per frame.

### `visibility` — the same question over a span

`layout --at N` is one frame, and the defect this exists for does not announce
which frame to look at. `visibility` sweeps evenly spaced frames — `--samples`,
default 24, first and last always included — and **fails when a node you gave a
`debugName` paints at some sampled frame and no sampled frame shows any part of
it**:

```
1 named node(s) paint and no sampled frame shows any of them:
  buried                                     covered at 24 of 24 sample(s), first at frame 0
```

```
2 named node(s) were shown and then covered at a later sampled frame:
  spanning                                   shown through frame 62, covered from 73 (7 shown, 17 covered, of 24)
  trailing                                   shown through frame 62, covered from 73 (7 shown, 3 covered, of 24)
```

Two readings, both about a node you named: it never appears at all, or it
appears and then something buries it for the rest of the film.
`compositions/occluded` is the first and `compositions/spanned` the second.
The second is the one that costs a delivery: a closing caption that the next
shot's footage paints over for most of its window, while `lint`, `check`,
`trace` and `diff` all pass — every one of them is right, and none of them is
about what is on screen. Paint order is document order, and nothing reorders
it for you. Covered *before* the last frame that shows it is a reveal, not a
burial, and passes.

**A dissolve is usually not a burial, and where it is, the check cannot tell.**
The outgoing half of a cross-fade contributes pixels for the whole overlap and
then stops emitting geometry, so it reads on-screen and then
invisible-by-declaration — never covered. That holds as long as the exit
reaches zero no later than the entrance turns opaque. Give the outgoing half a
1200 ms fade under a 400 ms one and its tail keeps painting for 24 frames with
every pixel hidden: that IS covered after being shown, and a named node in
that state fails even though the film is right. From the picture alone there
is nothing separating those frames from a caption the next shot ate. `spanned`
holds both dissolves side by side so the limit is a red case rather than a
sentence here — if you hit it, either finish the exit before the entrance
lands or leave that node unnamed.

Two things to know before you rely on it. **The name is the gate, and you have
to opt in.** A node with no `debugName` is reported and never failed on,
because unnamed nodes are in that state for correct reasons across the tree —
a text run that is a single space paints a glyph cell and covers no pixel, and
`reel`'s odometer digits ride an `overflow-hidden` strip that is mostly outside
its window. `baselines/visibility.json` counts them: 21 nodes across the tree
paint and are never shown, 19 of them in `reel` and unnamed, and the two that
are named are the `buried` nodes in `compositions/occluded` and
`compositions/layout-codes` — both fixtures, both recorded as failures.

Do not read the `debugName`s in this tree as evidence that naming is already
usual. `baselines/visibility.json` records the count per composition, and it is
the honest number rather than a memory: most of them are
`footage:<track>/tile:<col>:<row>`, which the footage binder refuses a track
without, and the rest are the fixtures — `reel`, the one composition here at
film length, records 0 named of 631 nodes. **Nothing names a caption unless
you do**, and a caption painted over is exactly what this gate is for. If you
want it to cover the thing
you would be upset to lose, put a `debugName` on it. **And a burial has to be
permanent to be seen.** The check asks whether any covered frame comes after
the last frame that showed the node, so a caption hidden behind something for
the middle of a shot and back by the end passes — and a covered stretch
shorter than the sampling stride can fall between two samples entirely. Raise
`--samples` to narrow that.

### `verify` — every gate, one envelope

```bash
bun src/cli/main.ts verify compositions/layout-codes --samples 3  # exit 1 — this fixture buries a named node on purpose
```

Runs `lint`, `check`, `keyframes`, `visibility`, `layout` at sampled frames,
and `assert`, in that order, and prints one JSON object:

```jsonc
{ "ok": false, "runId": "…", "strict": false,
  "errors": ["visibility"], "warnings": 50, "layoutFrames": [0, 15, 29],
  "lint": { … }, "realm": { … }, "keyframes": { … },
  "visibility": { … }, "layout": [ … ], "assertions": { … } }
```

**Each section is the sub-command's own JSON**, verbatim — the same object
`lint --json` prints, under the key `lint`; `layout` is one per sampled frame.
`tests/verify.test.ts` compares them field by field against those commands run
alone, because a section that had been re-shaped would be a second
implementation of the gate, and the second one is the one nobody tests.

An **error** is a section whose own verdict is false. A **warning** is an active
`layout` finding; `verify` exits 0 carrying warnings, and `--strict` makes them
count. `MOTION_RUN_ID` comes back as `runId` the way it does on every other
envelope — `applyEmit` attaches it, not this command.

`--samples N` and `--at a,b,c` decide the LAYOUT frames — five by default,
because a layout frame costs a boot. `visibility` and `assert` sweep their own
default grid, which is what makes those sections comparable to the commands
run alone. Everything that boots, boots: on a fixture that is seconds, on a
composition at film length it is minutes, and `--samples` is the only lever.

### `assert` — what the film is supposed to do

`lint` says the composition is well formed, `check` that the realm is clean,
`trace` that the frames are stable, `visibility` that a named node is shown at
all. None of them knows what the film is FOR. Write that down in the sidecar:

```jsonc
{ "motion": 1, "durationFrames": 240, "fps": 30,
  "assertions": [
    { "node": "caption",  "inPicture": [0, 71] },
    { "node": "lockup",   "entersBy": 40 },
    { "node": "lockup",   "exitsBy": 200 },
    { "node": "plate",    "insideBox": true },
    { "node": "caption",  "dwellFrames": 48 },
    { "node": "caption",  "before": "lockup" }
  ] }
```

One predicate per entry — two would be two assertions sharing one verdict, and
a reader could not tell which half failed. `node` is a `debugName`; a name the
tree does not carry is a FAILURE and not a skip, so renaming a node cannot turn
every assertion about it green at once.

Each one is evaluated from the picture, over the frames `assert` samples:

- `inPicture: [from, to]` — shown at every sampled frame in that window.
- `entersBy: f` — shown at some sampled frame at or before `f`.
- `exitsBy: f` — shown at no sampled frame after `f`.
- `insideBox: true` — no `escaped_container` and no `panel_out_of_canvas` at any
  sampled frame, `layoutAllow` applied.
- `dwellFrames: n` — the longest run of consecutive sampled frames showing it
  spans at least `n` composition frames. A run of one sample spans one frame,
  whatever the stride: the sweep saw the node at one instant and has no evidence
  about its neighbours.
- `before: other` — first shown strictly earlier than that other node.

**Every verdict is about the sampled frames and nothing between them**, and the
printed line names the grid it used. `--samples <durationFrames>` is the exact
case and costs what it costs. `assert` exits 1 on any failure.

**An assertion moves no pixel.** `identityProjection` drops the key, so adding
one does not change a recorded digest — `tests/identity.test.ts` proves that
rather than this sentence promising it.

Exit codes: 0 clean · 1 finding (lint failure, non-mount-only, divergence) ·
2 usage. `--frames N` limits any command's window, which makes short
iteration loops cheap; `--hash fast` speeds `trace`/`render` ~1.5× when the
digest is not going into a document.

The loop that closes without eyes: `lint` and `check` gate the contract;
`visibility` gates that what you named is on screen and stays there; `trace` run
twice proving the same digest is determinism, not luck; `frame` exists for when
you do want to look at a specific moment. A composition is done when `lint`,
`check` and `visibility` exit 0 and two `trace` runs agree — `render` is then
just encoding. A composition is *verified* when `bun scripts/digests.ts` and
`bun scripts/visibility.ts` have both been run over the tree it now belongs to.

## Determinism rules

The guest realm poisons everything environmental: `Date`, `Math.random`,
timers, `fetch`, `Intl`, locale methods. Touching one throws with the
alternative named in the error. Express randomness as constants decided in
`gen.ts` (the generator runs at build time and may do anything — its *output*
is what must be deterministic), time as the animation timeline, and data as
literals. Fonts and footage are inputs — their bytes are part of the render's
identity, never read from the machine's environment.
