# Synthetic clips and tones

Seven files nothing here fetches: three video clips and four sine tones,
generated by `ffmpeg` from `lavfi` sources. They are the inputs of the footage
and sound fixtures (`compositions/footage-tracks`, `compositions/sound-roles`)
and they exist so those two mechanisms can be exercised by a checkout that
carries no recorded material.

**The bytes are tracked**, and `.gitignore` carries an exception for them
because it ignores `*.mp4` everywhere. The reason is not size: footage is
decoded at build time and reaches the pak, so its bytes are one of the inputs
`src/render/identity.ts` hashes. A digest taken against a clip that only one
machine has is a digest only that machine can reproduce, which is the same
rule the tracked HarmonyOS Sans faces are here under.

**They are rebuildable, not merely verifiable.**
`manifest.json` carries, per file, the exact `ffmpeg` invocation, the first
line of `ffmpeg -version` from the run that produced the committed bytes, the
byte count and the SHA-256. Run the command again on the same ffmpeg and the
digest matches; `lavfi` sources and `libx264` at a fixed CRF are deterministic,
checked by generating each clip twice and comparing. Another ffmpeg build may
encode differently — that is why the version is recorded rather than assumed,
and why `bun scripts/assets.ts` verifies the digest of what is on disk instead
of re-running the command.

The manifest entries carry no `url`, so `scripts/assets.ts` treats them the
way it treats any generated asset: it verifies the digests and never claims it
can fetch them back.

`why` in the manifest says what each clip is for. Briefly: 24 does not divide
60, so that clip walks the ingest's resample path; the portrait clip and
the 2:1 clip have aspects that no drawn box in the fixture matches, which is
what `fit: "cover"` and `fit: "contain"` are declared against; the four tones
are one per sound role, at four frequencies so a mix can be read by ear as well
as by `sound --verify`.
